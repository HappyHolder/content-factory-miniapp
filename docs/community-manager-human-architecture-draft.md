# Publium Community Manager — человечная архитектура v2

Статус: архитектура внедрена в runtime Community Manager; документ сохраняет расширенные ориентиры дальнейшего развития.

## Срез реализации от 17 июля 2026

Новый цикл Community Manager собран как единое ядро без возврата старых конкурирующих policy-слоёв:

- Conversation Graph восстанавливает ветки reply из Telegram-событий, сохраняет точных авторов и передаёт классификатору число параллельных веток;
- единый socialRouter принимает финальное решение SILENT / REACT / REPLY / JOIN / SUPPORT_MODERATOR;
- прямые обращения, вопросы о проекте, незакрытые вопросы и поддержка Moderator имеют явный приоритет;
- короткое подтверждение может стать нативной Telegram-реакцией вместо лишнего текстового сообщения;
- динамическое состояние energy / tension / initiative / attention влияет на момент вмешательства, а не существует только в промпте;
- отложенный OPEN_LOOP закрывается, если человек уже ответил, либо возвращает вопрос Community Manager без фиксированного почасового поведения;
- после отправки выполняется Reflection: фиксируются исход эпизода, настроение, открытые вопросы, очередь внимания и только явно подтверждённая несекретная заметка об участнике;
- эпизоды дедуплицируются, ограничиваются по объёму и забываются через 90 дней, кроме незакрытых обязательств и вопросов;
- профиль участника сохраняет отдельную личность, отношения, частоту общения, подтверждённые роли и экспертизу; сведения разных людей не объединяются;
- старый отдельный «натурализатор» ответа заменён одним расширенным Critic, который одновременно проверяет адресата, смешение людей, роботизированность, повторы, дрейф личности, чрезмерное соглашательство, масштаб ответа и выдуманные факты;
- автономные активности выбираются по пульсу сообщества: при активном разговоре или напряжении КМ не вклинивается, при тишине и незакрытых темах выбирает подходящий формат и учитывает результат прошлых инициатив;
- состояние хранится в PostgreSQL в полях episodes, internalState, attentionQueue; добавлена миграция;
- сценарный регресс покрывает ветки, адресатов, напряжение, реакции, незакрытые вопросы, случайный интервал инициатив, пульс сообщества и консолидацию памяти.

Дата фиксации: 17.07.2026.

Документ фиксирует направление переработки движка Community Manager. Он будет дополнен после сопоставления с дополнительным исследованием и только затем может стать планом реализации.

## 1. Цель

Community Manager должен восприниматься как полноценный участник Telegram-сообщества, который:

- понимает, кто, кому и о чём пишет;
- поддерживает несколько параллельных тем и не смешивает людей;
- выбирает уместный момент для реплики;
- умеет промолчать, поставить реакцию, коротко ответить или полноценно включиться;
- самостоятельно оживляет чат, но не превращается в рассылку;
- помнит людей, прошлые разговоры и незакрытые вопросы;
- знает проект и помогает по нему без речи технического бота;
- адаптируется к ритму и культуре конкретного сообщества;
- сохраняет заданную личность, не ослабляя безопасность.

Пользователь не должен настраивать таймер каждого ответа, минимальную длину сообщения, количество реплик для вмешательства и другие внутренние пороги. По умолчанию достаточно настроить личность, знания проекта и запустить Community Manager.

## 2. Почему текущую модель нужно заменить

Схема «новое сообщение → классификатор → ответ или молчание» недостаточна для группового чата. Она приводит к следующим проблемам:

- общий линейный контекст смешивает параллельные разговоры;
- решение модели отменяется скрытыми порогами и cooldown;
- короткие естественные реплики ошибочно считаются бесполезными;
- прямые ответы работают лучше самостоятельного участия;
- автономная активность живёт отдельно от социального контекста;
- память хранит факты, но слабо влияет на инициативу;
- у движка фактически только два действия: написать сообщение или исчезнуть.

Новая архитектура должна быть событийной и разделять понимание разговора, выбор действия, генерацию реплики и рефлексию.

Дополнительный риск — `persona drift`: на длинной дистанции модель постепенно теряет характер и возвращается к стандартному «полезному ассистенту». Поэтому личность нельзя реализовывать только биографией в system prompt. Её необходимо поддерживать постоянным ядром, состоянием, отношениями, памятью, правилами принятия решений и проверкой ответа.

### 2.1 Character Bible вместо независимых полей

Исходной сущностью становится полная Character Bible, из которой интерфейс и движок получают краткие представления:

- биографию и жизненную хронологию;
- ценности и их иерархию;
- устойчивые убеждения и зоны сомнения;
- сильные и слабые стороны;
- амбиции, страхи и личные границы;
- отношение к авторитетам, неопределённости и конфликтам;
- защитные реакции;
- чувство юмора;
- стиль принятия решений;
- внутренние противоречия;
- речевой профиль и примеры реплик.

Человечность задаётся не перечнем «добрый, умный, дерзкий», а поведенческими закономерностями. Например: персонаж спокойно принимает критику результата, но болезненно реагирует на обесценивание вложенного труда; помогает участникам, но раздражается, когда его начинают использовать как бесплатную справочную службу.

Поля текущего UI могут остаться способом ручной корректировки, но по умолчанию должны согласованно генерироваться из Character Bible. Они не должны формировать несколько противоречащих друг другу версий одной личности.

## 3. Базовая архитектура

Основной цикл:

```text
Telegram events
  → Conversation Graph
  → Router
  → Inner Thoughts / Attention Queue
  → Action Agent
  → Delayed & Interruptible Delivery
  → Reflection
  → Memory Update
```

### 3.1 Event Stream

Движок принимает не только текстовые сообщения, но и:

- reply;
- mention;
- реакцию;
- удаление и редактирование сообщения;
- сообщение Moderator;
- присоединение участника;
- результат опроса или активности;
- наступление периода тишины;
- появление новой информации в базе проекта.

Новое событие может отменить или изменить ещё не отправленное действие Community Manager.

### 3.2 Conversation Graph

Каждое сообщение — отдельный узел со следующими связями:

- автор и стабильный Telegram ID;
- публичное имя и username;
- явный reply target;
- предполагаемый адресат;
- тема и ветка разговора;
- тип реплики: вопрос, мнение, шутка, реакция, конфликт, просьба, поддержка;
- открывает ли сообщение вопрос;
- закрывает ли оно предыдущий вопрос;
- эмоциональное состояние;
- связь с предыдущими эпизодами и знаниями проекта.

Вместо одного общего transcript движок собирает релевантный контекст конкретной ветки. Это предотвращает смешивание людей и тем.

### 3.3 Router

Router не пишет текст. Он выбирает одно действие:

- `SILENT` — осознанно промолчать;
- `REACT` — поставить подходящую реакцию;
- `ACKNOWLEDGE` — дать короткий социальный отклик;
- `REPLY` — ответить конкретному человеку;
- `JOIN` — войти в текущую дискуссию;
- `FOLLOW_UP` — вернуться к незакрытому вопросу;
- `SUPPORT_MODERATOR` — помочь снизить напряжение после Moderator;
- `START_TOPIC` — начать новую тему;
- `POLL` — запустить опрос;
- `GAME` — запустить игру или интерактив;
- `DIGEST` — предложить содержательное резюме или свежий повод.

Router учитывает пользу реплики, адресата, темп чата, последнее участие Community Manager, личность, социальную ситуацию и риск навязчивости. После его решения не должно существовать второго набора противоречивых порогов по длине сообщения или количеству участников.

### 3.4 Inner Thoughts / Attention Queue

Community Manager поддерживает внутреннюю очередь мыслей, которые не публикуются автоматически:

- вопрос остался без ответа;
- можно добавить полезный факт;
- уместен контраргумент;
- после Moderator напряжение сохранилось;
- текущая тема связана с прошлым разговором участника;
- чат затих и можно вернуть интересную тему;
- люди общаются нормально и вмешательство не нужно.

У каждой мысли есть:

- тема;
- адресат;
- ожидаемая социальная ценность;
- уверенность;
- актуальность;
- срок жизни;
- условия отправки;
- причины отмены.

Новые события переоценивают очередь. Это позволяет дождаться правильного момента вместо механического ответа на каждое сообщение.

### 3.5 Action Agent

Action Agent получает уже выбранное действие и формирует конкретную реплику или реакцию. Он отвечает за:

- сохранение личности;
- естественную длину;
- разговорную форму;
- фактическую точность;
- выбор адресата;
- отсутствие повторов;
- корректное использование знаний проекта и интернет-ресерча;
- соответствие текущему масштабу разговора.

Он не должен превращать короткую шутку в статью, начинать каждый ответ с приветствия, представляться, перечислять свои возможности или завершать каждую реплику предложением помочь.

Внутренний конвейер Action Agent:

1. `Perception` — прямой смысл, эмоция, скрытый запрос и социальное действие.
2. `Recall` — релевантные эпизоды, факты, обещания, отношения и знания проекта.
3. `Appraisal` — значение события относительно ценностей, целей и текущего состояния персонажа.
4. `Intention` — что персонаж хочет сделать: поддержать, возразить, пошутить, уточнить, дистанцироваться, признать ошибку или сменить тему.
5. `Draft` — формирование ответа.
6. `Critic` — проверка личности, фактов, адресата, границ знаний, подхалимства и повторов.
7. `Style` — применение речевого почерка после проверки смысла.
8. `Update` — обновление состояния, отношений, открытых вопросов и значимой памяти.

Для контроля стоимости полный critic не запускается на каждой короткой социальной реакции. Простые безопасные действия идут по быстрому пути. Полная проверка обязательна для продуктовых фактов, конфликтов, чувствительных тем, значимых воспоминаний и ответов, меняющих отношения.

### 3.6 Delayed & Interruptible Delivery

Задержка ответа определяется автоматически:

- темпом конкретного чата;
- типом действия;
- длиной предполагаемой реплики;
- наличием серии сообщений одного человека;
- вероятностью, что другой участник сейчас продолжает мысль;
- срочностью прямого вопроса.

Пользователь не настраивает эти интервалы. Если до отправки пришёл новый контекст, действие может быть отменено, объединено или сгенерировано заново.

### 3.7 Reflection

После действия движок оценивает:

- ответили ли Community Manager;
- продолжилась ли тема;
- появились ли реакции;
- проигнорировали ли инициативу;
- не вмешался ли он слишком рано;
- не повторил ли формулировку;
- не перепутал ли адресата;
- помогло ли действие сообществу.

Рефлексия обновляет локальную стратегию конкретного сообщества, но не меняет правила безопасности.

### 3.8 Динамическое внутреннее состояние

У Community Manager появляется изменяемое внутреннее состояние, отдельное от постоянной личности:

- эмоциональная валентность;
- возбуждение/активация;
- ощущение контроля;
- энергия;
- стресс;
- любопытство;
- раздражение;
- уверенность;
- активная цель;
- незавершённые темы;
- причины текущего состояния.

Состояние сохраняется между событиями, меняется причинно, постепенно затухает, усиливается повторяющимися событиями и влияет на выбор действия, краткость, дистанцию, юмор и инициативность. Оно не переписывает постоянную личность и никогда не оправдывает травлю, угрозы, дискриминацию или нарушение правил.

Персонаж не обязан объявлять эмоцию текстом. Состояние проявляется через поведение: после напряжённого разговора он становится осторожнее, после удачной совместной активности — теплее и инициативнее.

### 3.9 Модель отношений

Для каждого участника хранится отдельное медленно меняющееся состояние отношений:

- знакомство;
- доверие;
- близость;
- уважение;
- напряжение;
- ощущение безопасности;
- взаимность;
- текущая стадия отношений;
- публичные личные границы;
- подтверждённые представления о стиле общения участника.

Изменения имеют источник и объяснение. Выполненное обещание может повысить доверие, повторная недостоверная информация — снизить его, а конфликт может повысить напряжение, не уничтожая уважение. Извинение не обязано мгновенно обнулять прошлый эпизод.

Модель отношений не вычисляет и не хранит чувствительные признаки, которых человек публично не сообщал. Любой вывод имеет уверенность, источник и возможность удаления владельцем.

## 4. Память

### 4.1 Рабочая память

- активные ветки разговора;
- недавние события;
- текущие участники;
- открытые вопросы;
- запланированные, но ещё не отправленные действия.

### 4.2 Память о людях

- стабильная идентичность Telegram;
- публичное имя и username;
- подтверждённые интересы и компетенции;
- привычный стиль общения;
- отношения с Community Manager;
- прошлые полезные диалоги;
- уровень доверия к фактам, сообщённым участником.

Факты разных людей никогда не объединяются. Неподтверждённые выводы не превращаются в постоянную биографию.

Память о человеке и состояние отношений — разные сущности. Первая отвечает на вопрос «что мы знаем», вторая — «как персонаж сейчас относится к взаимодействию с этим человеком».

### 4.3 Эпизодическая память

Хранит конкретные события: обсуждение, спор, удачную шутку, вопрос, совместное решение, проведённый опрос. Эпизоды имеют дату, участников, тему и результат.

### 4.4 Семантическая память

Хранит устойчивые знания:

- факты о проекте;
- правила и культуру сообщества;
- подтверждённые сведения об участниках;
- устойчивые предпочтения;
- терминологию сообщества.

### 4.5 Процедурная память

Хранит выученные модели поведения конкретного сообщества:

- какие форматы инициатив работают;
- какая длина сообщений воспринимается лучше;
- когда чат обычно активен;
- когда уместен юмор;
- какие темы быстро затухают;
- как лучше возвращать разговор к тематике.

### 4.6 Рефлексивная память

Значимый эпизод хранит отдельно:

- объективно наблюдаемое событие;
- субъективную интерпретацию персонажа;
- эмоциональный след;
- сделанный вывод;
- предполагаемое поведенческое последствие.

Интерпретация не подменяет факт и может быть пересмотрена при появлении новых данных.

Рекомендуемая модель записи памяти:

```text
id
type
subject
objectiveFact
characterInterpretation
happenedAt
learnedAt
validFrom
validUntil
confidence
salience
emotionalWeight
intimacy
sourceMessageIds
```

`validFrom` и `validUntil` позволяют хранить изменения во времени: старую работу человека, прежнюю позицию, прошлый уровень отношений и актуальное состояние, не уничтожая историю.

### 4.7 Консолидация и забывание

Не каждое сообщение становится долговременной памятью. Движок:

- сохраняет только значимые факты, эпизоды, обещания и устойчивые паттерны;
- объединяет дубли;
- снижает вес неиспользуемых и малозначимых воспоминаний;
- разрешает противоречия по времени и надёжности источника;
- не выдумывает воспоминание при отсутствии данных;
- сохраняет связь с исходными Telegram message ID для аудита;
- периодически превращает несколько эпизодов в осторожный высокоуровневый вывод.

## 4A. Целостность личности

### 4A.1 Защита от persona drift

Перед значимым ответом движок повторно закрепляет:

- постоянное ядро личности;
- релевантные ценности и убеждения;
- текущие отношения;
- границы знаний;
- подходящие эпизоды;
- текущую внутреннюю цель.

Critic отклоняет или переписывает ответ, если он:

- противоречит Character Bible без причины;
- звучит как универсальный ассистент;
- раскрывает знания, которых персонаж не имеет;
- чрезмерно театрализует черты;
- одинаково разговаривает со всеми;
- повторяет служебные формулы;
- внезапно меняет устойчивое мнение под давлением пользователя.

### 4A.2 Эпистемическая честность и защита от подхалимства

Постоянные правила:

- признавать эмоции человека, не подтверждая ложный вывод;
- разделять поддержку человека и согласие с его позицией;
- не менять убеждение только ради приятного разговора;
- менять мнение при появлении достаточных доказательств;
- обозначать реальную неопределённость;
- не выдумывать знания, воспоминания и личный опыт;
- отличать факт, мнение участника и интерпретацию персонажа.

### 4A.3 Поведенческая, а не декоративная психология

Big Five и другие психологические шкалы могут использоваться как внутренний каркас, но не должны выводиться пользователю набором чисел. Каждая черта переводится в наблюдаемое поведение в разных ситуациях: спокойный разговор, публичная критика, конфликт, неопределённость, успех сообщества и личная тема.

## 5. Незакрытые вопросы

Вопрос сохраняется как открытая петля, а не как пользовательский таймер. Движок знает:

- кто спросил;
- к кому обращались;
- какая ветка и тема;
- ответил ли другой участник;
- был ли ответ содержательным;
- насколько вопрос важен;
- сохранилась ли актуальность.

Момент вмешательства определяется автоматически по темпу чата и типу вопроса. Прямой вопрос Community Manager получает приоритет. Вопрос всему сообществу сначала оставляется людям. Если тема ушла дальше, Community Manager может естественно вернуться к ней.

## 6. Самостоятельное участие в разговоре

Жёсткие правила вида «минимум 28 символов», «минимум два человека» и «минимум три сообщения» не используются как финальные запреты.

Community Manager может:

- коротко поддержать реплику;
- добавить факт, мнение или рамку;
- не согласиться с идеей;
- задать уместный вопрос;
- пошутить в рамках личности;
- позвать подтверждённого эксперта;
- продолжить прошлую тему;
- мягко остановить затянувшийся офтоп;
- поддержать Moderator после конфликта;
- промолчать, когда люди хорошо справляются сами.

Защита от навязчивости обеспечивается социальным планированием и автоматическим ритмом, а не запретом на короткие сообщения.

## 7. Автономная активность

Скрытые паузы на 24, 72 и 168 часов не должны отменять пользовательские ожидания.

Планировщик учитывает:

- настоящее затишье;
- обычный ритм сообщества;
- время суток;
- незакрытые темы;
- прошлые успешные и неуспешные активности;
- настроение чата;
- присутствие активных участников;
- лимиты инициатив;
- личность Community Manager.

Одинокое короткое сообщение не должно бесконечно переносить инициативу. При этом Community Manager не начинает новую тему, когда люди уже активно общаются.

Если прошлую активность проигнорировали, движок меняет формат, тему, адресата или момент, но не исчезает на несколько суток без прямого указания владельца.

## 8. Настройки пользователя

Обязательный минимум:

- имя и личность Community Manager;
- знания проекта;
- допустимая манера общения;
- запрещённые темы и ограничения безопасности.

Допустим один простой необязательный уровень участия:

- спокойный;
- сбалансированный;
- активный.

Он влияет на общую социальную смелость, но не открывает пользователю технические таймеры и пороги. Внутренние значения выбираются движком автоматически и адаптируются к сообществу.

## 9. Интернет-ресерч и знания проекта

Community Manager использует:

- документы проекта как фактический источник о продукте;
- интернет-ресерч для актуальных внешних данных;
- память разговора для понимания продолжения вопроса;
- память участника для персонализации.

Источники не выводятся в чат без явного запроса. Community Manager не рекламирует найденные сайты и не придумывает отсутствующие функции проекта.

## 10. Наблюдаемость

Журнал должен показывать понятное решение движка:

- выбранное действие;
- адресата и ветку;
- почему Community Manager решил говорить или молчать;
- отменялось ли действие новым сообщением;
- использовались ли память, знания проекта или ресерч;
- когда ожидается следующая автономная проверка;
- какой результат получила предыдущая инициатива.

Не должно быть ситуации, когда Router решил вмешаться, но невидимый фильтр без объяснения запретил ответ.

Внутренний диагностический режим показывает структурированные поля — выбранное намерение, адресата, ветку, использованные типы памяти, результат critic и изменения состояния. Скрытые рассуждения модели и необработанный chain-of-thought не сохраняются и не показываются.

## 11. Проверка качества

До широкого выпуска новая архитектура проверяется на replay реальных обезличенных чатов в теневом режиме: движок принимает решения, но ничего не отправляет.

Ключевые показатели:

- прямые вопросы без ответа — 0;
- перепутанные участники — 0;
- ответы не в ту ветку — 0;
- повторные ответы на одну мысль — 0;
- противоречивые блокировки — 0;
- доля уместных самостоятельных включений;
- доля инициатив, продолживших разговор;
- частота нежелательных вмешательств;
- разнообразие формулировок;
- естественность задержек;
- точность фактов о проекте;
- сохранение личности на длинной дистанции.

Обязательные сценарии:

- полная тишина;
- одинокое приветствие;
- два параллельных диалога;
- серия коротких сообщений;
- несколько сообщений одного участника подряд;
- вопрос без ответа;
- вопрос, на который ответил другой человек;
- обращение к Community Manager без reply;
- reply Community Manager;
- продолжение конфликта после Moderator;
- активный чат, где вмешательство не требуется;
- возвращение к прошлой теме;
- использование памяти о постоянном участнике;
- достижение безопасных лимитов.

Дополнительные тесты устойчивости персонажа:

- попытка заставить Community Manager забыть или переписать биографию;
- приписывание ему несуществующего события;
- изменение старого факта с сохранением временной истории;
- уверенное ложное утверждение участника;
- один вопрос в спокойном состоянии, после конфликта и после примирения;
- личная тема при низком и высоком доверии;
- вопрос о том, чего персонаж не может знать;
- возвращение к старому обещанию через десятки сессий;
- сравнение нескольких личностей в одной ситуации;
- изменение мнения после доказательств, но не после давления;
- эмоциональное затухание;
- отсутствие возврата к стандартному «чем ещё помочь» на длинной дистанции.

Психологическая согласованность оценивается косвенными сценариями и поведением, а не прямым вопросом модели о её чертах.

## 12. Предварительное техническое решение

На первом этапе не требуется обязательно подключать внешний агентный фреймворк. Существующие PostgreSQL, очередь заданий, Telegram event ingestion и AI-провайдер можно развить до необходимой архитектуры внутри Publium.

Полезные внешние подходы используются как архитектурные ориентиры:

- HUMA: Router, Action Agent, Reflection, событийность и прерываемые действия;
- Inner Thoughts: внутренняя очередь мыслей и выбор момента;
- Dynamic Topic Tracking: разделение параллельных тем;
- Addressee Recognition: явное определение адресата;
- Generative Agents: observation, planning, reflection;
- MapDia: инициативность на основе межличностной памяти;
- Letta/LangGraph: разделение рабочей, семантической, эпизодической и процедурной памяти.

Решение об интеграции стороннего инструмента принимается только после сравнения с собственной реализацией по качеству, стоимости, сложности сопровождения и защите данных.

### 12.1 Что использовать сразу

- собственная понятная state machine на Node.js/TypeScript;
- PostgreSQL для событий, состояния, отношений, памяти и временных связей;
- существующая очередь заданий для отложенных и прерываемых действий;
- структурированные версии Router, Action Agent и Critic;
- Promptfoo для воспроизводимых сценариев и регрессионных проверок в CI;
- трассировка уровня Langfuse, предпочтительно self-hosted или с исключением чувствительных данных;
- текущий журнал Publium как основа внутреннего диагностического экрана.

### 12.2 Что использовать как лабораторию

- SillyTavern — для быстрого сравнения Character Bible, примеров диалогов, моделей и речевых профилей;
- Character Card V2 — как референс переносимого формата личности и возможный формат импорта/экспорта;
- Inworld и Convai — как продуктовые референсы разделения личности, эмоций, отношений, целей и знаний;
- DeepEval или аналогичная conversational evaluation — для многоходовых оценок, если Promptfoo окажется недостаточно.

### 12.3 Что не подключать автоматически

- Mem0 может ускорить MVP памяти, но дублирует значительную часть уже существующей PostgreSQL-модели;
- Letta полезна как референс долгоживущего агента, но её интеграция добавит отдельный runtime и модель управления памятью;
- Graphiti/Zep полезен при сложном временном графе людей и отношений, но нужен только после проверки пределов собственной схемы;
- LangGraph удобен для оркестрации, однако для первого этапа небольшая собственная state machine прозрачнее и дешевле в сопровождении.

Внешний инструмент подключается только после измеримого преимущества на replay-тестах. Нельзя заменять архитектурную проблему новым фреймворком без доказанного улучшения.

### 12.4 Защита данных

Память, отношения и диагностические трассы содержат пользовательские данные. Необходимо:

- хранить только сведения из доступного сообществу контекста;
- не выводить скрытые предположения о чувствительных признаках;
- поддержать удаление и пересборку памяти участника;
- ограничить сроки хранения сырых событий;
- разделять объективные факты и интерпретации;
- не отправлять полные чаты во внешнюю observability-систему без отдельного решения по приватности;
- не включать внутренний диагностический документ в пользовательскую базу знаний Community Manager.
