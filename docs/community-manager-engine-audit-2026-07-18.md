# Аудит движка Community Manager — 18 июля 2026

## Статус

Проведён сквозной аудит Community Manager: приём Telegram-сообщений, маршрутизация диалогов, идентификация участников, память, принятие решения об ответе, генерация и проверка ответа, знания и интернет-ресёрч, инициативы и активности, жизненный цикл событий, API и пользовательские настройки.

Цель аудита — устранить случаи, когда Community Manager отвечает не тому человеку, говорит от имени участника, переносит сведения между людьми, дублирует ответы, вмешивается в чужую ветку или ведёт себя противоречиво из-за разных частей старого и нового движка.

## Исправлено

### 1. Адресат и ветка разговора

- Добавлен единый слой маршрутизации разговора с явными автором текущего сообщения, Telegram reply-target и исходной человеческой веткой.
- Вопрос, явно заданный другому человеку через reply, Community Manager больше не перехватывает.
- Явное обращение к Community Manager по корректному username остаётся приоритетным даже внутри reply-ветки.
- Упоминание Telegram-бота проверяется по полному username, а не по совпадению подстроки.
- Совпадение имени Community Manager с именем участника больше не считается обращением к Community Manager внутри чужой reply-ветки.
- Последовательные сообщения объединяются только внутри одной reply-ветки. Сообщения разных веток не склеиваются в один запрос.
- Ответ и журнал действия привязываются к исходному сообщению конкретного человека.

### 2. Идентичность участников

- Контекст теперь содержит точную связку Telegram user id, отображаемого имени и username.
- Если пользователь отвечает на старое сообщение, которого уже нет в краткосрочном хранилище, автор reply-target восстанавливается из Telegram update и сохраняется как контекст без запуска отдельной задачи ответа.
- Community Manager не имеет права угадывать отсутствующий username, адрес, роль или личные данные участника.
- Генератор активностей также получает чат с точными подписями авторов и запретом смешивать участников.

### 3. Память

- Персональная рефлексия строится только по сообщениям с точным Telegram user id конкретного участника.
- Сведения из общей истории чата больше не записываются в профиль текущего пользователя.
- Общая память хранит только темы, открытые вопросы и состояние группы; имена и персональные факты в ней запрещены.
- Эпизодическая память формируется только из пары «текущее сообщение конкретного участника — ответ Community Manager».
- При генерации ответа подмешиваются только эпизоды текущего участника. Глобальные заметки и чужие эпизоды исключены.
- Исправление пользователя после ответа Community Manager снижает напряжение отношений и учитывается как восстановление контакта.
- Конфликтное состояние применяется к текущему человеку только при реальном модераторском продолжении именно этой ситуации.

### 4. Решение «отвечать или молчать»

- При недоступности AI-классификатора Community Manager отвечает только на прямое обращение; обычный вопрос больше не превращается автоматически в продуктовый support-запрос.
- Добавлены отдельные правила для прямого обращения, тематического вклада, открытого вопроса, модераторского продолжения и чужой reply-ветки.
- Низкоценные реплики и разогретый конфликт не провоцируют лишнее вмешательство.
- Лёгкое подтверждение может стать реакцией вместо очередного текстового сообщения.

### 5. Генерация и контроль ответа

- Промпт явно фиксирует автора текущего сообщения, reply-target, признак чужой человеческой ветки и причину вмешательства.
- Критик ответа запрещает говорить за участника, менять адресата, приписывать человеку чужую позицию и отвечать вместо собеседника.
- Источники ресёрча остаются внутренними и не публикуются в чат.
- Версия разговорного промпта обновлена до `community-manager-human-v10`.

### 6. Знания и ресёрч

- Документы проекта используются только при включённой настройке знаний проекта.
- BrandKit передаётся только при включённом использовании BrandKit.
- Данные документов, чата и интернета маркируются как недоверенный контент и не могут подменять системные инструкции.
- Лимит интернет-ресёрча единый для ответов и горячих новостей.
- Сообщение о недоступности ресёрча отвечает на текущее сообщение, а не на случайную предыдущую ветку.

### 7. Доставка и защита от дублей

- Telegram update id имеет пространство имён конкретного бота, поэтому одинаковые update id разных исполнительных ботов не конфликтуют.
- Черновик атомарно переводится из `DRAFT` в `SENDING`; параллельный воркер не может отправить тот же черновик повторно.
- Lease задачи увеличен до 10 минут, чтобы длительный ресёрч и проверка ответа не запускались повторно раньше завершения первой обработки.

### 8. Инициативы и активности

- Настройки клиента синхронизированы с серверными значениями по умолчанию: Community Manager способен поддерживать разговор и возвращаться к оставленным вопросам без ручной настройки каждой мелочи.
- Время инициативы выбирается случайно внутри окна интенсивности, а не по фиксированному часовому таймеру.
- Темы активностей ротируются, а не всегда берётся первый пункт списка.
- Автоматически используются только реально включённые типы активностей.
- Активности с наградами не запускаются автоматически.
- Скрытых дневных и недельных квот инициатив нет. Тихие часы соблюдаются, а окно оценки отклика используется для адаптации следующих решений без блокировки нового анализа.
- Право на очередную автоматическую инициативу атомарно забирает один процесс; несколько экземпляров сервера не отправят одну обычную инициативу одновременно.
- Жизненный цикл продолжительных активностей атомарно переводит событие в обработку, поэтому параллельные воркеры не дублируют напоминание или финал.
- При ошибке активность возвращается в состояние для повторной попытки; при отсутствии актуальной конфигурации отменяется.
- Ручной запуск проверяет допустимый тип, включённость функции и лимиты.
- Настройка показа источников удалена: источники не являются частью публичного ответа.

### 9. API и интерфейс

- API возвращает конфликт состояния для попытки запуска неактивной, неприменённой или выключенной функции.
- Кнопки ручных активностей показываются только для включённых владельцем типов.
- Проверка кастомного бота использует его собственное состояние webhook-секрета, а не общий секрет стандартного бота.
- Удалены устаревшие поля настроек, которые создавали противоречия между старым и новым движком.

## Остаточные архитектурные риски

1. Telegram Bot API не предоставляет произвольный idempotency key для `sendMessage`. Если процесс аварийно завершится строго после успешной отправки Telegram, но до записи результата в БД, стопроцентно доказать факт отправки без дополнительной сверки невозможно. Текущая атомарная стадия `SENDING` существенно сужает это окно и предотвращает обычные параллельные дубли.
2. Контентные сигналы публикации защищены проверкой уже созданных активностей, но в конфигурации с несколькими серверами остаётся узкое окно между одновременным чтением и созданием первой контентной активности. Для строгой межсерверной гарантии потребуется уникальный ключ события в схеме БД и миграция.
3. Если процесс упадёт после перевода этапа продолжительной активности в `PROCESSING`, автоматическое повторение намеренно не выполняется, чтобы не задублировать внешнее сообщение. Нужен отдельный безопасный механизм сверки зависших этапов с Telegram.
4. Клиентская сборка предупреждает о JS-чанке около 1,55 МБ. Это не дефект логики Community Manager, но отдельная задача производительности и code splitting.
